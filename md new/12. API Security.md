# BOOKS VIEW — API Security

## 1. Mục đích

Tài liệu này quy định các nguyên tắc bảo mật cho toàn bộ API của BOOKS VIEW — Photo Gallery & Guest Selection Platform.

Phạm vi chỉ tập trung vào BOOKS VIEW:

- Album ảnh.
- Gallery.
- Guest.
- Primary Customer.
- Like / Star / Comment.
- Download.
- Google Drive.
- Authentication.
- Database/API.
- Dữ liệu và quyền truy cập ảnh.

Không bao gồm các hệ thống quản lý nhân viên, tài chính, dịch vụ, lịch hẹn hoặc phần mềm khác.

---

# 2. Nguyên tắc cốt lõi

> **Frontend không phải nơi quyết định quyền. API/server mới là nơi quyết định quyền.**

Mọi dữ liệu gửi từ browser đều phải được coi là không đáng tin cậy.

Luồng API chuẩn:

```text
Browser
   ↓
Request
   ↓
Rate Limiting
   ↓
Authentication
   ↓
Authorization
   ↓
Input Validation
   ↓
Business Rules
   ↓
Database
   ↓
Safe Response
```

Không được bỏ qua các bước bảo mật chỉ vì frontend đã kiểm tra.

---

# 3. Authentication — Xác định người gửi request

Authentication trả lời:

> **Người đang gửi request là ai?**

## 3.1. Studio/Admin

BOOKS VIEW có thể hỗ trợ:

- Email + Password.
- Google OAuth.

Sau khi đăng nhập thành công, server tạo session an toàn.

Các API admin phải xác định được user hiện tại trước khi cho thực hiện thao tác bảo vệ.

Ví dụ:

```text
Admin
 ↓
Login
 ↓
Session
 ↓
API
```

Nếu chưa xác thực:

```text
401 Unauthorized
```

## 3.2. Customer

Customer có thể được xác thực thông qua:

- Album link/token.
- Guest identity.
- Primary Customer password.
- Customer session.

Không được nhầm Album Token với quyền Admin.

---

# 4. Authorization — Kiểm tra quyền

Authentication = **Mày là ai?**

Authorization = **Mày có quyền làm việc này không?**

Ví dụ:

```text
User A
 ↓
Đã đăng nhập
 ↓
GET Album B
 ↓
User A không có quyền
 ↓
403 Forbidden
```

Server phải kiểm tra quyền với resource thực tế.

Không được chỉ ẩn nút trên giao diện.

Ví dụ Guest không nhìn thấy nút Star là chưa đủ. Nếu Guest tự gọi:

```text
POST /api/selections
```

với:

```json
{
  "likeType": "STAR"
}
```

server vẫn phải từ chối.

---

# 5. Input Validation

Tất cả dữ liệu từ browser đều phải được kiểm tra ở server.

Các dữ liệu cần validate:

```text
Tên
SĐT
Email
Album ID
Photo ID
Selection
Comment
Password
Album Token
Query parameters
Pagination
Sort/filter parameters
Upload metadata
```

TypeScript chỉ kiểm tra kiểu dữ liệu trong code.

Ví dụ:

```typescript
const phone: string = request.body.phone;
```

không có nghĩa `phone` hợp lệ.

Các giá trị sau đều có thể là string:

```text
"0901234567"
"abc"
"hello"
"123"
```

Vì vậy phải có validation về nghiệp vụ và format.

# 6. Rate Limiting

Rate limiting giới hạn số request trong một khoảng thời gian.

Mục tiêu:

- Chống brute force.
- Chống spam.
- Chống bot.
- Giảm API abuse.
- Giảm tải bất thường lên server/database.

Các API nên được rate limit:

```text
Login
Guest authentication
Primary Customer password
Comment
Like
Star
Download
Album access
Google Drive sync
Các API nhạy cảm khác
```

Ví dụ:

```text
Bot
 ↓
POST /api/auth/login
 ↓
rất nhiều request
 ↓
Rate Limit
 ↓
429 Too Many Requests
```

---

# 7. Request Size / Request Limits

Rate limiting kiểm soát **số lần gọi**.

Request limit kiểm soát **mỗi request được phép lớn/đắt đến mức nào**.

Ví dụ Comment:

```text
≤ 1.000 ký tự
```

Không cho:

```text
Comment = 50 MB
```

Ví dụ API photo list:

Không cho:

```text
/api/photos?limit=1000000
```

Nên đặt giới hạn tối đa, ví dụ:

```text
limit ≤ 100
```

Con số cụ thể có thể điều chỉnh theo kiến trúc thực tế.

# 8. Không trả dữ liệu thừa

API chỉ trả những dữ liệu frontend thực sự cần.

Ví dụ database Customer có:

```text
id
name
phone
email
passwordHash
sessionToken
internalNotes
```

API gallery không được trả toàn bộ object nếu client chỉ cần:

```json
{
  "id": "abc",
  "name": "Nguyễn Văn A"
}
```

Không trả:

```text
passwordHash
sessionToken
internalNotes
secret
thông tin nội bộ không cần thiết
```

Nguyên tắc:

> **Database object không đồng nghĩa với API response object.**

Nên dùng response/DTO riêng cho API.

# 9. Không trả Secret

Các secret phải ở server/environment variables.

Ví dụ:

```text
DATABASE_URL
GOOGLE_DRIVE_API_KEY
GOOGLE_CLIENT_SECRET
AUTH_SECRET
OAUTH_SECRET
```

Không được trả các giá trị này về browser.

Không hard-code secret trong frontend.

Không đặt secret thành:

```text
NEXT_PUBLIC_*
```

nếu secret đó không cần public.

Không commit secret vào GitHub.

---

# 10. Không trả Stack Trace Production

Khi server gặp lỗi, không trả stack trace cho khách.

Không trả:

```text
PrismaClientKnownRequestError
/var/task/...
node_modules/...
database connection...
```

Thay vào đó:

```json
{
  "success": false,
  "error": {
    "code": "INTERNAL_ERROR",
    "message": "Có lỗi xảy ra. Vui lòng thử lại."
  }
}
```

Chi tiết lỗi chỉ nằm trong server log nội bộ.

---

# 11. Không để lộ Database Error

Prisma/PostgreSQL có thể trả các lỗi nội bộ.

Không đưa trực tiếp lỗi database vào response.

Ví dụ không trả:

```text
relation "Photo" does not exist
```

hoặc:

```text
PrismaClientKnownRequestError
```

cho khách.

Server phải:

1. Ghi log lỗi nội bộ.
2. Gán request ID nếu cần.
3. Trả message an toàn cho client.

---

# 12. HTTP Status Codes

API nên sử dụng status code rõ ràng.

## 400 — Bad Request

Dữ liệu gửi lên không hợp lệ.

```text
400 Bad Request
```

## 401 — Unauthorized

Chưa xác thực.

```text
401 Unauthorized
```

## 403 — Forbidden

Đã xác thực nhưng không có quyền.

```text
403 Forbidden
```

## 404 — Not Found

Resource không tồn tại hoặc không nên được tiết lộ.

```text
404 Not Found
```

## 429 — Too Many Requests

Quá nhiều request.

```text
429 Too Many Requests
```

## 500 — Internal Server Error

Lỗi server.

Không trả stack trace hoặc database details.

# 13. IDOR / BOLA Protection

Đây là phần cực kỳ quan trọng.

Không được cho phép người dùng thay đổi ID trong URL/request để truy cập resource của người khác.

Ví dụ:

```text
/api/albums/123
```

Không được để người dùng đổi thành:

```text
/api/albums/124
```

và xem album không thuộc quyền của họ.

Tương tự:

```text
Photo
Selection
Comment
Customer
Album
```

Server phải kiểm tra quan hệ:

```text
Current User
      ↓
Album
      ↓
Photo
      ↓
Selection / Comment
```

# 14. Album → Photo → Customer Authorization

Đối với BOOKS VIEW, mọi thao tác quan trọng phải kiểm tra resource có thuộc đúng album hay không.

Ví dụ:

```text
Customer A
 ↓
Album A
 ↓
Photo A
```

Nếu Customer A gửi:

```text
photoId = Photo B
```

server phải kiểm tra:

```text
Photo B thuộc Album A?
```

Nếu không:

```text
Reject
```

Không được chỉ tìm Photo bằng ID rồi cho thao tác.

---

# 15. Like / Star API Security

Ví dụ:

```text
POST /api/selections
```

Client gửi:

```json
{
  "photoId": "123",
  "likeType": "STAR"
}
```

Server phải kiểm tra:

```text
1. Request có hợp lệ?
2. Customer/session là ai?
3. Customer thuộc album?
4. Photo tồn tại?
5. Photo thuộc album?
6. Album còn active?
7. Customer có quyền Star?
8. Selection có hợp lệ?
9. maxSelectionCount có bị vượt?
10. Database transaction có an toàn?
```

Guest không được tự gửi `STAR` để vượt qua giao diện.

---

# 16. maxSelectionCount

Nếu album có:

```text
maxSelectionCount = 50
```

server phải đảm bảo khách không thể vượt quá giới hạn do:

- Click liên tục.
- Mở nhiều tab.
- Gửi request song song.
- Race condition.
- Gọi API trực tiếp.

Việc kiểm tra phải được thực hiện ở server/database, không chỉ frontend.

# 17. Comment API Security

Comment phải:

- Plain text.
- Validate ở server.
- Giới hạn độ dài.
- Rate limit.
- Không render HTML không an toàn.
- Không thực thi JavaScript.
- Kiểm tra Photo thuộc Album.
- Kiểm tra Customer/session thuộc Album.

Không dùng:

```tsx
dangerouslySetInnerHTML
```

cho comment khách nếu không có cơ chế sanitize phù hợp.

# 18. Download API Security

Download phải kiểm tra quyền trước khi trả ảnh.

Luồng:

```text
Download request
      ↓
Authentication
      ↓
Authorization
      ↓
Photo thuộc Album?
      ↓
Customer có quyền download?
      ↓
Có được phép tải ảnh?
      ↓
Authorized download
```

Không nên để một URL download riêng tư tồn tại vĩnh viễn nếu không cần.

# 19. Google Drive API Security

Google Drive API key phải nằm ở server/environment variable.

Không đưa API key vào client nếu không cần.

Không expose:

```text
GOOGLE_DRIVE_API_KEY
```

cho browser.

API sync Drive phải là API được bảo vệ dành cho Studio/Admin.

Ví dụ:

```text
POST /api/albums/{id}/sync-drive
```

Server phải kiểm tra:

```text
Admin session?
 ↓
Có quyền album?
 ↓
Album có googleDriveFolderId?
 ↓
Sync
```

# 20. Session Security

Session cần:

- Token/session ID khó đoán.
- Có thời hạn.
- Có thể revoke.
- Cookie `HttpOnly`.
- Cookie `Secure` khi production.
- `SameSite` phù hợp.
- Không lưu credential nhạy cảm trong `localStorage`.

Nên tách rõ:

```text
Admin Session
```

và:

```text
Customer Session
```

không để quyền của loại này tự động trở thành quyền của loại kia.

# 21. CSRF

```text
POST
PUT
PATCH
DELETE
```

cần có cơ chế CSRF phù hợp với kiến trúc authentication/session.

Đặc biệt:

```text

Like
Star
Comment
Change Password
Change Album
```

# 22. Upload API Security

Nếu BOOKS VIEW có upload ảnh local:

- Allowlist định dạng.
- Kiểm tra MIME.
- Kiểm tra file signature/content.
- Giới hạn dung lượng.
- Giới hạn kích thước.
- Không tin filename.
- Đổi tên file phía server.
- Chống path traversal.
- Không cho upload file thực thi.
- Xử lý ảnh qua `sharp` theo pipeline của app.

Ví dụ:

```text
IMG_1234.JPG
```

không nhất thiết được lưu bằng tên do người dùng cung cấp.

# 25. API Response thống nhất
