# BOOKS VIEW — Comment Security

## 1. Mục đích

Tài liệu này quy định cách bảo vệ chức năng Comment của BOOKS VIEW.

Comment của khách phải được xem là **dữ liệu văn bản không đáng tin cậy**. Nội dung khách nhập không được phép trở thành HTML, JavaScript hoặc mã thực thi trên trình duyệt.

Mục tiêu:
- Ngăn XSS.
- Ngăn HTML Injection.
- Ngăn JavaScript Injection.
- Không cho script trong comment được thực thi.
- Giữ trải nghiệm comment đơn giản, dễ dùng.
- Bảo vệ khách khác, studio và dữ liệu album.

## 2. Nguyên tắc bất di bất dịch

> **Comment = Plain Text.**

BOOKS VIEW không cần cho khách viết HTML trong comment.

Ví dụ khách nhập:

```html
<script>alert("XSS")</script>
```

BOOKS VIEW phải hiển thị nguyên văn dưới dạng chữ và **không được thực thi JavaScript**.

Tương tự:

```html
<h1>Ảnh này đẹp</h1>
```

phải được hiển thị như text, không biến thành tiêu đề HTML.

## 3. XSS — Cross-Site Scripting

XSS xảy ra khi dữ liệu do khách nhập được đưa trở lại trang web theo cách khiến trình duyệt thực thi JavaScript.

Ví dụ:

```html
<script>alert("Hacked")</script>
```

hoặc:

```html
<img src="x" onerror="alert('XSS')">
```

Không được để các nội dung này thực thi khi người khác mở album.

Luồng an toàn:

```text
Khách nhập Comment
        ↓
Server nhận dữ liệu
        ↓
Validate
        ↓
Lưu dạng text
        ↓
Database
        ↓
React render text
        ↓
Hiển thị cho khách
```

## 4. HTML Injection

Không cho comment trở thành HTML.

Ví dụ:

```html
<h1>Hello</h1>
```

Không được render thành tiêu đề. Phải hiển thị:

```text
<h1>Hello</h1>
```

Không cho khách sử dụng comment để chèn HTML element, iframe, style, form, event handler hoặc nội dung có khả năng phá giao diện/tạo hành vi không mong muốn.

## 5. JavaScript Injection

Không cho comment chứa JavaScript được thực thi.

Ví dụ:

```text
javascript:alert("XSS")
```

hoặc:

```html
<img src="x" onerror="alert('XSS')">
```

đều phải được coi là text hoặc xử lý an toàn, tuyệt đối không trở thành mã chạy trên trình duyệt.

## 6. Không dùng HTML rendering không an toàn

Với comment từ khách, ưu tiên render text thông thường của React:

```tsx
<div>{comment.content}</div>
```

Không đưa trực tiếp nội dung comment vào:

```tsx
dangerouslySetInnerHTML
```

nếu chưa có cơ chế sanitize phù hợp.

Nguyên tắc:

> **Không cần HTML thì không render HTML.**

## 7. Validation phía server

Không chỉ kiểm tra comment ở frontend.

Frontend validation phục vụ UX; security phải nằm ở server:

```text
Frontend
   ↓
API
   ↓
Server Validation
   ↓
Authorization
   ↓
Database
```

Người dùng có thể bỏ qua giao diện và gọi API trực tiếp, vì vậy server luôn phải kiểm tra lại dữ liệu.

## 8. Giới hạn comment

Comment nên có giới hạn hợp lý:

- Không cho comment rỗng.
- Giới hạn số ký tự.
- Xử lý khoảng trắng dư thừa khi cần.
- Không cho request có payload bất thường quá lớn.
- Rate limit để chống spam.

Ví dụ:

```text
Comment tối đa: 1.000 ký tự
```

Con số cụ thể có thể điều chỉnh theo UX thực tế.

## 9. Unicode, tiếng Việt và Emoji

Comment phải hỗ trợ bình thường:

```text
Ảnh này đẹp quá ❤️
```

Cho phép tiếng Việt, Unicode, Emoji và ký tự đặc biệt thông thường.

Không vì lý do bảo mật mà chặn toàn bộ ký tự đặc biệt một cách máy móc.

## 10. Nhận diện khách có cùng tên

Trong album event/kỷ yếu, có thể có nhiều người cùng tên.

Không ép người dùng phải có tên hoàn toàn khác.

Nếu phát hiện tên đã tồn tại trong cùng album, BOOKS VIEW nên nhắc:

> **Tên này đã có người sử dụng. Vui lòng thêm 1 ký tự hoặc nickname để phân biệt.**

Ví dụ:

```text
Nguyễn Minh Anh
```

đã tồn tại.

Người tiếp theo có thể nhập:

```text
Nguyễn Minh Anh 1
Nguyễn Minh Anh A
Minh Anh - Lớp 12A1
Bắp
```

Mục đích là **phân biệt người chọn ảnh**, đặc biệt khi studio xem Selection Manager.

Không nên tự ý sửa tên khách.

## 11. Không dùng tên làm định danh duy nhất

Tên khách chỉ dùng để hiển thị/phân biệt.

Không dùng:

```text
customer.name
```

làm khóa duy nhất.

Phải có ID riêng:

```text
Customer
├── id
├── name
├── phone
└── ...
```

Hai người cùng tên vẫn là hai Customer khác nhau.

## 12. Comment phải thuộc đúng Photo và Album

Khi nhận comment, server phải kiểm tra:

```text
Photo tồn tại?
      ↓
Photo thuộc Album?
      ↓
Customer/session thuộc Album?
      ↓
Album còn hoạt động?
      ↓
Comment hợp lệ?
      ↓
Lưu
```

Không được tin `photoId` hoặc `albumId` do browser gửi lên.

## 13. Không để khách comment vào album khác

Khách ở Album A không thể sửa request để dùng `photoId` của Album B rồi tạo comment cho Album B.

Đây là một phần của Authorization/IDOR protection.

## 14. Không để khách sửa comment của người khác

Nếu BOOKS VIEW cho phép sửa/xóa comment, server phải xác định comment đó thuộc Customer/session nào.

Không được chỉ dựa vào `commentId`.

## 15. Rate Limit Comment

Để tránh spam:

```text
Khách
 ↓
Comment
 ↓
API
 ↓
Rate Limit
```

Có thể giới hạn theo session/IP và album tùy kiến trúc.

Mục tiêu:
- Chống spam comment.
- Chống bot.
- Giảm abuse API.
- Không làm ảnh hưởng khách bình thường.

## 16. Không log dữ liệu nhạy cảm không cần thiết

Server log có thể ghi:

```text
commentId
albumId
customerId
timestamp
```

Không log password, session token hoặc secret.

Nếu nội dung comment không cần cho debugging thì không nên đưa toàn bộ nội dung vào log production.

## 17. Database

Comment được lưu trong database dưới dạng dữ liệu.

Không thực thi nội dung comment trong database.

Luồng:

```text
Database
   ↓
API
   ↓
React
   ↓
Text
```

## 18. Security Test bắt buộc

### Test 1 — Script

```html
<script>alert("XSS")</script>
```

Kết quả: **Không chạy JavaScript.**

### Test 2 — HTML

```html
<h1>Hello</h1>
```

Kết quả: **Hiển thị như text.**

### Test 3 — Event handler

```html
<img src=x onerror=alert(1)>
```

Kết quả: **Không thực thi.**

### Test 4 — JavaScript URL

```text
javascript:alert(1)
```

Kết quả: **Không thực thi.**

### Test 5 — Comment cực dài

Gửi payload vượt giới hạn.

Kết quả: **Server từ chối request.**

### Test 6 — Spam

Gửi nhiều comment liên tục.

Kết quả: **Rate limit / cooldown.**

### Test 7 — Cross Album

Thử dùng `photoId` của album khác.

Kết quả: **Server từ chối.**

## 19. Quy tắc triển khai cho Claude

Khi Claude sửa Comment, phải:
1. Không thay đổi UI Comment nếu không được yêu cầu.
2. Không dùng `dangerouslySetInnerHTML` cho comment khách nếu không có lý do và cơ chế sanitize rõ ràng.
3. Validate ở server.
4. Authorization ở server.
5. Giới hạn độ dài.
6. Rate limit.
7. Giữ Unicode/tiếng Việt/emoji.
8. Không dùng tên khách làm unique ID.
9. Kiểm tra Photo thuộc đúng Album.
10. Không để comment có thể thực thi HTML/JavaScript.
11. Không làm thay đổi Selection/Like/Star logic ngoài phạm vi cần thiết.
12. Không làm ảnh hưởng Gallery/Lightbox hiện tại.

## 20. Tiêu chuẩn hoàn thành

```text
✓ Comment là plain text
✓ XSS không chạy
✓ HTML Injection không chạy
✓ JavaScript Injection không chạy
✓ Server validation
✓ Client validation cho UX
✓ Giới hạn độ dài
✓ Rate limit
✓ Authorization
✓ Photo thuộc đúng Album
✓ Customer/session thuộc đúng Album
✓ Không dùng tên làm unique ID
✓ Hỗ trợ tên trùng bằng ký tự/nickname
✓ Unicode tiếng Việt
✓ Emoji
✓ Không expose secret
✓ Không log secret
✓ Không render HTML không an toàn
```

## Nguyên tắc cuối cùng

> **BOOKS VIEW không cần biến Comment thành một trình soạn thảo HTML. Comment chỉ là văn bản của khách.**

Điều này giúp chức năng Comment đơn giản hơn, an toàn hơn và phù hợp với mục đích của BOOKS VIEW.
