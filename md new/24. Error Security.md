# 24. ERROR SECURITY — BOOKS VIEW

## 1. Mục đích

Khi BOOKS VIEW xảy ra lỗi trong production, người dùng chỉ nhận được thông báo an toàn và dễ hiểu.

Thông tin kỹ thuật chi tiết phải được ghi ở server log để Developer/Operator có thể kiểm tra.

Mô hình:

```text
ERROR
  ↓
Central Error Handler
  ├──→ Server Log
  │      ↓
  │   Chi tiết lỗi
  │   Stack Trace
  │   Request ID
  │
  └──→ User
         ↓
   Thông báo an toàn
```

---

# 2. Không expose lỗi kỹ thuật cho người dùng

Production không được trả cho browser các thông tin nội bộ như:

```text
Prisma error
Database URL
Database password
file path
server path
stack trace
secret
API key
OAuth secret
session token
internal IDs không cần thiết
SQL/database details
```

Không được trả nguyên lỗi kiểu:

```text
PrismaClientKnownRequestError...
```

cho người dùng.

Thay vào đó:

```text
Có lỗi xảy ra. Vui lòng thử lại.
```

---

# 3. Prisma Error

Không được trả trực tiếp object `error` từ Prisma về client.

Không nên:

```text
catch (error) {
    return Response.json(error)
}
```

vì lỗi có thể chứa thông tin nội bộ.

Luồng đúng:

```text
Database Operation
 ↓
Prisma Error
 ↓
Server Log chi tiết
 ↓
Generic Response cho Client
```

Client chỉ nhận thông báo an toàn.

---

# 4. Database URL

Không được để Database URL xuất hiện trong response.

Ví dụ nguy hiểm:

```text
postgresql://user:password@host/database
```

Thông tin này chỉ được sử dụng phía server/environment.

Nếu database xảy ra lỗi:

```text
Database Error
 ↓
Server Log
```

không:

```text
Database Error
 ↓
Browser
```

---

# 5. File Path / Server Path

Không trả đường dẫn hệ thống cho người dùng.

Ví dụ:

```text
/Users/duytran/Projects/BOOKS VIEW/...
```

hoặc:

```text
/vercel/path0/frontend/src/...
```

Không cần thiết cho client và có thể tiết lộ cấu trúc hệ thống.

Client chỉ nhận:

```text
Có lỗi xảy ra. Vui lòng thử lại.
```

---

# 6. Stack Trace

Production không được hiển thị stack trace cho người dùng.

Không:

```text
Error
    at PrismaClient...
    at /app/src/lib/...
    at processTicksAndRejections...
```

Stack trace chỉ dành cho:

```text
Server Log
Monitoring
Debugging
```

---

# 7. Secret và API Key

Không được expose:

```text
DATABASE_URL
GOOGLE_DRIVE_API_KEY
GOOGLE_CLIENT_SECRET
AUTH_SECRET
OAUTH_SECRET
```

hoặc bất kỳ secret/API key nào.

Nếu lỗi có chứa secret thì secret cũng không được đưa vào response.

Server log cũng phải tránh log nguyên secret.

---

# 8. Internal ID

Không phải mọi Internal ID đều là secret.

Tuy nhiên API chỉ nên trả dữ liệu mà client thực sự cần.

Ví dụ nếu frontend chỉ cần:

```text
Album
Photo
```

thì không cần trả các thông tin nội bộ như:

```text
internalRecordId
migrationId
internalJobId
```

Nguyên tắc:

> API chỉ trả dữ liệu cần thiết cho client.

---

# 9. Error Message an toàn

Thay vì:

```text
PrismaClientKnownRequestError...
```

trả:

```text
Có lỗi xảy ra. Vui lòng thử lại.
```

Có thể sử dụng format:

```json
{
  "error": "INTERNAL_SERVER_ERROR",
  "message": "Có lỗi xảy ra. Vui lòng thử lại."
}
```

Nếu cần hỗ trợ debug, có thể thêm `requestId` không nhạy cảm:

```json
{
  "error": "INTERNAL_SERVER_ERROR",
  "message": "Có lỗi xảy ra. Vui lòng thử lại.",
  "requestId": "REQ-8F29A1"
}
```

---

# 10. Request ID

Request ID giúp Developer tìm chính xác lỗi trong server log.

Ví dụ User nhận:

```text
Có lỗi xảy ra. Vui lòng thử lại.

Mã lỗi: REQ-8F29A1
```

Server log:

```text
REQ-8F29A1
 ↓
POST /api/comments
 ↓
Prisma Error
 ↓
Stack Trace
 ↓
Timestamp
```

Khi người dùng báo mã:

```text
REQ-8F29A1
```

Developer có thể tìm đúng request.

---

# 11. Server Log

Server vẫn phải ghi lỗi chi tiết.

Có thể ghi:

```text
Error Type
Timestamp
Request ID
Endpoint
HTTP Method
User/Session context phù hợp
Stack Trace
Prisma Error
```

Nhưng không ghi:

```text
Password
Session Token
API Key
Database Password
Secret
```

---

# 12. Development và Production

Có thể có sự khác biệt:

### Development

Developer cần thông tin chi tiết:

```text
Prisma Error
Stack Trace
Debug Information
```

### Production

Người dùng chỉ nhận:

```text
Có lỗi xảy ra. Vui lòng thử lại.
```

Không được vô tình bật debug error cho production.

---

# 13. Login và Account Enumeration

Error Security cũng cần tránh làm lộ thông tin tài khoản.

Không nên trả các thông báo quá khác nhau như:

```text
Email không tồn tại
```

và:

```text
Email tồn tại nhưng password sai
```

nếu điều đó cho phép attacker dò email đã đăng ký.

Có thể sử dụng thông báo chung:

```text
Email hoặc mật khẩu không chính xác.
```

---

# 14. Error Code cho Frontend

Frontend có thể nhận một mã lỗi an toàn:

```json
{
  "error": "REQUEST_FAILED",
  "message": "Có lỗi xảy ra. Vui lòng thử lại."
}
```

Frontend có thể dựa vào `error` để hiển thị giao diện phù hợp.

Không gửi thông tin debug trong response.

---

# 15. Central Error Handler

BOOKS VIEW nên có cơ chế xử lý lỗi API thống nhất.

Luồng:

```text
API Request
 ↓
try / catch
 ↓
Central Error Handler
 ├── Log chi tiết
 └── Response an toàn
```

Không nên để mỗi API xử lý lỗi một kiểu.

Các API như:

```text
/api/albums
/api/photos
/api/comments
/api/selections
/api/download
/api/admin/*
```

nên tuân theo quy tắc Error Security chung.

---

# 16. HTTP Status Code

Nên sử dụng HTTP status code phù hợp.

```text
400
→ Request không hợp lệ

401
→ Chưa xác thực

403
→ Không có quyền

404
→ Không tìm thấy / không nên tiết lộ resource

409
→ Conflict

429
→ Quá nhiều request

500
→ Lỗi server
```

Response vẫn phải tránh lộ thông tin nội bộ.

```text
POST /api/comments

```

# 18. ADMIN cũng không được nhận Secret

Dù request đến từ ADMIN:

```text
ADMIN
 ↓
API Error
```

cũng không được trả:

```text
DATABASE_URL
API_KEY
AUTH_SECRET
Server Path
Stack Trace
```

Quyền quản trị không đồng nghĩa với quyền xem infrastructure secrets.

---

# 19. Error Security và API Security

Error Security phải hoạt động cùng các lớp bảo mật khác:

```text
Request
 ↓
Rate Limit
 ↓
Authentication
 ↓
CSRF
 ↓
Authorization
 ↓
Validation
 ↓
Business Rules
 ↓
Database
 ↓
Error Handler
```

Nếu xảy ra lỗi:

```text
Error
 ↓
Server Log chi tiết
 ↓
Safe Response
```

---

# 20. Checklist Error Security

```text
□ Không trả Prisma error cho User
□ Không trả Database URL
□ Không trả Database password
□ Không trả file path
□ Không trả server path
□ Không trả stack trace production
□ Không trả secret
□ Không trả API key
□ Không trả OAuth secret
□ Không trả session token
□ Không trả internal ID không cần thiết
□ Không expose SQL/database details
□ Không expose infrastructure details
□ Có generic error message
□ Có HTTP status code phù hợp
□ Có thể sử dụng Request ID
□ Log lỗi chi tiết ở server
□ Không log password
□ Không log session token
□ Không log API key/secret
□ Development có thể debug
□ Production không expose debug information
□ API có error format thống nhất
□ Không làm lộ thông tin tài khoản không cần thiết
```

---

# 21. Nguyên tắc cuối cùng

```text
USER
 ↓
Safe Error Message
```

và:

```text
SERVER
 ↓
Detailed Error Log
```

> **User cần biết chuyện gì xảy ra ở mức đủ để sử dụng hệ thống. Developer cần biết chi tiết để sửa lỗi. Hai loại thông tin này không nên giống nhau.**

Mục tiêu của Error Security không phải là giấu lỗi khỏi Developer, mà là ngăn lỗi kỹ thuật nội bộ trở thành thông tin cho người dùng hoặc attacker.
