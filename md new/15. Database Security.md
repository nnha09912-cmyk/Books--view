# BOOKS VIEW — Database Security

## 1. Mục đích

Tài liệu này quy định các nguyên tắc bảo mật cho PostgreSQL và lớp truy cập database của BOOKS VIEW.

BOOKS VIEW hiện sử dụng:

```text
Next.js
TypeScript
Prisma ORM
PostgreSQL
```

Database có thể chứa các dữ liệu quan trọng của hệ thống:

```text
Album
Photo
Customer
Selection
Like
Star
Comment
```

Vì vậy database phải nằm phía sau server và không được cho browser truy cập trực tiếp.

Production PostgreSQL phải sử dụng credential an toàn.

Connection string thường có dạng:

```env
DATABASE_URL="postgresql://username:password@host:5432/booksview"
```

Có thể chứa:

```text
Database host
Username
Password
Port
Database name
Connection information
```

Không dùng password đơn giản như:

```text
123456
password
booksview
admin123
```

Nên sử dụng credential mạnh/ngẫu nhiên và phù hợp với hệ thống database đang dùng.

# 7. Prisma Query an toàn

BOOKS VIEW sử dụng Prisma ORM.

Ưu tiên Prisma query API:

```typescript
const photo = await prisma.photo.findUnique({
  where: {
    id: photoId,
  },
});
```

Không tự ghép SQL string từ dữ liệu người dùng.

Không nên:

```typescript
const query = `
  SELECT * FROM photos
  WHERE id = '${photoId}'
`;
```

---

# 8. SQL Injection

SQL Injection xảy ra khi input của người dùng được đưa trực tiếp vào câu SQL theo cách làm thay đổi logic câu query.

Ví dụ nguy hiểm:

```typescript
const query = `
  SELECT * FROM photos
  WHERE id = '${photoId}'
`;
```

Người dùng có thể cố tình gửi input đặc biệt để phá cấu trúc câu SQL.

Vì vậy:

> **Không nối chuỗi SQL với dữ liệu người dùng.**

Ưu tiên Prisma query API.

---

# 9. Prisma không có nghĩa là an toàn tuyệt đối

Prisma giúp việc query an toàn hơn khi sử dụng API thông thường.

Tuy nhiên vẫn phải cẩn thận với raw SQL.

Đặc biệt không sử dụng:

```typescript
prisma.$queryRawUnsafe(...)
```

một cách tùy tiện.

Nếu thực sự cần raw SQL:

- Phải parameterize đúng cách.
- Không ghép input người dùng trực tiếp vào SQL.
- Chỉ dùng khi có lý do kỹ thuật rõ ràng.

Nguyên tắc:

> **Prisma query API là lựa chọn mặc định.**

# 11. Chống IDOR / BOLA

Ví dụ:

```text
User A
 ├── Album 123
 └── Album 124
```

User A không có quyền:

```text
Album 999
```

Nếu user thay đổi:

```text
/api/albums/123
```

thành:

```text
/api/albums/999
```

server phải kiểm tra quyền.

Nếu không có quyền:

```text
403 Forbidden
```

hoặc response phù hợp với chiến lược bảo mật của API.

Không được chỉ dựa vào ID.

---

# 12. Kiểm tra Album → Photo → Customer

Đây là quy tắc đặc biệt quan trọng của BOOKS VIEW.

Ví dụ:

```text
Album A
 ├── Photo A1
 ├── Photo A2
 └── Photo A3
```

Customer thuộc Album A.

Nếu request gửi:

```text
photoId = Photo B1
```

server phải kiểm tra:

```text
Photo B1
    ↓
Thuộc Album A?
    ↓
Không
    ↓
Reject
```

Không được chỉ:

```typescript
prisma.photo.findUnique({
  where: { id: photoId }
});
```

rồi cho phép thao tác mà không kiểm tra context Album/Customer.

# 13. Không trả nguyên Database Object

Không nên mặc định:

```typescript
const customer = await prisma.customer.findUnique(...);

return Response.json(customer);
```

nếu object chứa dữ liệu frontend không cần.

Database có thể có:

```text
id
name
phone
email
passwordHash
sessionToken
internalNotes
...
```

API chỉ nên trả:

```json
{
  "id": "abc",
  "name": "Nguyễn Văn A"
}
```

Nguyên tắc:

> **Database object không đồng nghĩa với API response object.**

Chỉ trả field cần thiết.

---

# 14. Password không được lưu Plain Text

Nếu BOOKS VIEW có password authentication:

Không lưu:

```text
password = "123456"
```

trực tiếp trong database.

Phải sử dụng password hashing phù hợp.

Luồng:

```text
Password người dùng
        ↓
Hash
        ↓
Database
```

Khi đăng nhập:

```text
Password nhập
        ↓
Verify
        ↓
Hash stored password
        ↓
Đúng → Login
Sai → Reject
```

Không lưu password thật.

---

# 15. Database User phải có quyền phù hợp

Không nên cấp quyền database rộng hơn nhu cầu.

Nguyên tắc:

> **Least Privilege — chỉ cấp quyền tối thiểu cần thiết.**

Application database user chỉ nên có quyền cần cho BOOKS VIEW.

Không nên dùng một database credential có quyền quản trị toàn bộ hệ thống nếu ứng dụng không cần.

# 19. Transaction cho thao tác quan trọng

Một số thao tác cần đảm bảo tính nhất quán.

Ví dụ Selection có:

```text
maxSelectionCount
```

Nếu nhiều request chạy đồng thời:

```text
Request A
Request B
Request C
```

chỉ kiểm tra frontend là không đủ.

Các thao tác cần nhiều bước database có thể cần transaction:

```text
Request
 ↓
Validation
 ↓
Transaction
 ↓
Check current state
 ↓
Insert/Update
 ↓
Commit
```

Mục tiêu:

- Tránh race condition.
- Tránh vượt giới hạn.
- Giữ dữ liệu nhất quán.

```text
1. API này là public hay protected?
2. Authentication có cần không?
3. User/customer là ai?
4. Có quyền với resource không?
5. Input có hợp lệ không?
6. Resource có tồn tại không?
7. Resource có thuộc đúng Album không?
```

# 31. Nguyên tắc cuối cùng

> **Database là khu vực phía sau server, không phải tài nguyên của browser.**

Kiến trúc bắt buộc:

```text
                         INTERNET
                             │
                             ▼
                         Browser
                             │
                           HTTPS
                             │
                             ▼
                    BOOKS VIEW API
                             │
               ┌─────────────┼─────────────┐
               │             │             │
        Authentication  Authorization  Validation
               │             │             │
               └─────────────┼─────────────┘
                             │
                           Prisma
                             │
                             ▼
                        PostgreSQL
```

Không bao giờ:

```text
Browser
   │
   ├── DATABASE_URL ❌
   ├── PostgreSQL password ❌
   └── Direct PostgreSQL connection ❌
```

> **Browser chỉ yêu cầu. API quyết định. Prisma truy vấn. PostgreSQL lưu trữ.**

Đây là nguyên tắc nền tảng để bảo vệ dữ liệu Album, Photo, Customer, Selection, Like, Star và Comment của BOOKS VIEW.
