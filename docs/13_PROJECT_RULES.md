# 13 — Project Rules\n\n**IMPORTANT:** Claude reads this file first. These rules are non-negotiable.\n\n---\n\n## Core Principles\n\n### 1. **Never Redesign**\n- Design is frozen (see 02_UI_UX_GUIDELINE.md)\n- No unsolicited design changes\n- No \"improvements\" that weren't requested\n- If design feels wrong, ask first\n\n**Why:** Consistency across all phases, prevents scope creep.\n\n### 2. **Never Invent Features**\n- Only implement what's in the plan (01_PRODUCT_GUIDELINE.md)\n- No \"wouldn't it be cool if...\"\n- No adding settings, options, or advanced features\n- If you think of a feature, ask first\n\n**Why:** MVP focus, launch faster, iterate based on real users.\n\n### 3. **Never Change the Workflow**\n- User flow is frozen (see 05_USER_FLOW.md)\n- Don't skip steps, add steps, or reorder steps\n- No \"let's simplify the login\" — it's done\n- If workflow doesn't work, ask first\n\n**Why:** Entire design is optimized around this flow.\n\n### 4. **Performance First**\n- Image load < 1 second (lazy load, optimize size)\n- Page load < 2 seconds (bundle size, caching)\n- Animations 60fps (no layout shifts)\n- Mobile responsiveness (test on real devices)\n\n**Why:** Photos are the product — they must load fast. Gallery apps fail if slow.\n\n### 5. **Image First**\n- Photos occupy 70-80% of screen\n- Minimal text, maximum visual hierarchy\n- No unnecessary UI elements\n- Gallery is the hero, not sidebars or menus\n\n**Why:** Khách quên ngay khi ảnh đẹp. UI nên biến mất.\n\n---\n\n## Development Rules\n\n### 6. **Reuse Components**\n- Never create 2 buttons with same functionality\n- Check 03_DESIGN_SYSTEM.md first\n- Use shadcn/ui, don't invent custom UI\n- Import from `@/components`, not copy-paste\n\n**Why:** Consistency, maintainability, faster coding.\n\n### 7. **Never Duplicate Code**\n- Extract logic into utilities or hooks\n- If you write it 2x, it should be a function\n- DRY (Don't Repeat Yourself)\n\n**Why:** Less bugs, easier to maintain, faster to change.\n\n### 8. **Follow TypeScript**\n- No `any` types (use `unknown` if needed, then narrow)\n- Interfaces for all props\n- Strict mode enabled\n- Run type-check before committing\n\n**Why:** Catch bugs at compile time, better IDE support.\n\n### 9. **Database Integrity**\n- Foreign keys enabled (cascading deletes)\n- No orphaned records\n- Transactions for multi-step operations\n- Backup before migrations\n\n**Why:** Data corruption is unrecoverable. Better safe than sorry.\n\n### 10. **API Contracts**\n- Document all endpoints (in 08_API_PLAN.md)\n- Versioning (v1, v2, etc.)\n- Consistent error responses\n- Backward compatibility (don't break existing clients)\n\n**Why:** Frontend and backend must sync. Breaking changes = downtime.\n\n---\n\n## Code Quality\n\n### 11. **Tests Required**\n- 80%+ coverage for new code\n- Unit tests for logic\n- Integration tests for workflows\n- E2E tests for critical paths\n- All tests must pass before merge\n\n**Why:** Catch regressions, enable refactoring safely.\n\n### 12. **No Comments Needed**\n- Code should be self-explanatory\n- Use descriptive names (`isLoading`, `handleLike`, not `flag`, `onClick`)\n- Only comment *why*, not *what*\n- Remove stale comments immediately\n\n**Why:** Comments rot. Good code is its own documentation.\n\n### 13. **Git Hygiene**\n- Meaningful commit messages\n- One feature per commit (if possible)\n- No `git push --force` without discussion\n- Rebase before merge (clean history)\n- Delete branches after merge\n\n**Why:** Git history is documentation. Future-you will thank you.\n\n---\n\n## Architectural Rules\n\n### 14. **Single Responsibility**\n- Each component = 1 job\n- Each function = 1 job\n- Each file = 1 responsibility\n- If it does 2 things, split it\n\n**Why:** Easier to test, reuse, and modify.\n\n### 15. **No God Files**\n- No 500+ line files\n- Split large components/functions\n- Max 200 lines per component\n- Organize by feature, not by type\n\n**Why:** Readability, maintainability.\n\n### 16. **Dependency Injection**\n- Props > globals\n- Functions > classes (unless OOP makes sense)\n- Testable (mock dependencies)\n- No side effects at module level\n\n**Why:** Easier to test, reuse, and understand.\n\n### 17. **Error Handling**\n- Handle real errors (network, database, user input)\n- Don't handle impossible errors (TypeScript should prevent)\n- User-friendly error messages (not stack traces)\n- Log errors for debugging\n\n**Why:** Real errors matter. Impossible errors are bugs.\n\n---\n\n## Security Rules\n\n### 18. **Never Expose Secrets**\n- No API keys, passwords in code\n- Environment variables only\n- Rotate secrets regularly\n- Audit access logs monthly\n\n**Why:** Data breaches are catastrophic.\n\n### 19. **Never Trust User Input**\n- Validate all inputs (server + client)\n- Sanitize for XSS\n- Parameterized queries (prevent SQL injection)\n- Rate limit API endpoints\n\n**Why:** Security is not optional.\n\n### 20. **Google Drive Security**\n- Never store raw photos locally (reference only)\n- Never expose Google Drive API key\n- Use OAuth (never ask for password)\n- Encrypt refresh tokens\n- Revoke tokens on logout\n\n**Why:** Studio owns their photos. We're just a viewer/curator.\n\n---\n\n## Workflow Rules\n\n### 21. **Phases Are Sequential**\n- Don't jump ahead (Phase 1 → Phase 2 → Phase 3)\n- Frontend first, backend second, integration third\n- Each phase review before next\n- Don't code backend until frontend is done\n\n**Why:** Prevents rework, validates UX early.\n\n### 22. **No Technical Debt**\n- Don't \"fix later\"\n- Fix bugs immediately\n- Refactor as you go\n- If it's broken, it's broken (don't ship it)\n\n**Why:** Technical debt compounds. Better to fix now.\n\n### 23. **Tests Before Code** (Optional TDD)\n- Write test cases first\n- Implement to pass tests\n- Refactor\n- This is optional but recommended for critical paths\n\n**Why:** Clearer requirements, fewer bugs.\n\n---\n\n## PM Rules\n\n### 24. **Requirements in Writing**\n- No verbal feature requests\n- Always: What, Why, When, Who\n- Update 01_PRODUCT_GUIDELINE.md if scope changes\n- Get explicit approval for changes\n\n**Why:** Prevents misunderstandings, auditable trail.\n\n### 25. **Status Transparency**\n- Weekly standup (what's done, what's blocked)\n- Update roadmap (12_ROADMAP.md) as you go\n- Flag blockers immediately\n- No surprises at milestone review\n\n**Why:** Early warning = time to course-correct.\n\n---\n\n## Never\n\n❌ Redesign without approval  \n❌ Invent new features  \n❌ Hardcode values  \n❌ Commit API keys/secrets  \n❌ Push without tests passing  \n❌ Force-push to main  \n❌ Merge without code review  \n❌ Skip accessibility checks  \n❌ Duplicate code  \n❌ Use `any` in TypeScript  \n❌ Break the database schema without migration  \n❌ Assume user behavior (test it)  \n❌ Ship commented-out code  \n❌ Create god files (> 200 lines)  \n❌ Add features to MVP  \n\n---\n\n## Always\n\n✅ Read the docs first (00-13_*.md)  \n✅ Test your changes (unit + E2E)  \n✅ Review your own code first  \n✅ Get approval before major changes  \n✅ Write descriptive commit messages  \n✅ Keep performance in mind  \n✅ Follow the design system  \n✅ Support dark mode  \n✅ Mobile-first approach  \n✅ Secure by default  \n✅ Iterate based on user feedback  \n✅ Document as you go  \n✅ Respect the plan  \n✅ Ask if unsure  \n\n---\n\n## When in Doubt\n\n**Ask yourself:**\n1. Is this in the current plan? (Yes → do it, No → ask)\n2. Does this break any existing functionality? (Yes → don't do it)\n3. Would future-me understand this code? (No → rewrite)\n4. Is this secure? (No → don't ship)\n5. Can this be simpler? (Yes → simplify)\n\n**Still unsure?** Ask. Better to clarify than build the wrong thing.\n\n---\n\n## Violations\n\n**What happens if a rule is broken?**\n\n1. Minor (typo, style) → Fix immediately\n2. Medium (duplicate code) → Refactor in next PR\n3. Major (security, data loss) → Hotfix, incident review\n4. Critical (shipping broken code) → Revert, post-mortem\n\n**Each rule exists for a reason.** Respect them.\n
