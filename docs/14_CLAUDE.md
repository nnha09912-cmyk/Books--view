Read the relevant doc (e.g., 05_USER_FLOW.md for features)\n2. Check if it's in scope for current phase\n3. Identify affected components/files\n4. Then code\n\n### While Coding\n- Follow TypeScript + Tailwind conventions\n- No hardcoded values (use design tokens)\n- No copy-paste (reuse components)\n- Tests as you go (not after)\n- Commit often with clear messages\n\n### After Coding\n- Self-review (lint, types, tests)\n- Verify on mobile (responsive)\n- Check dark mode\n- Performance check (Lighthouse)\n- Summarize changes (what + why)\n\n---\n\n## For Design Questions\n\n### If design question:\n1. Check 02_UI_UX_GUIDELINE.md + 03_DESIGN_SYSTEM.md\n2. If answer is there, use it\n3. If not, propose a solution based on principles\n4. Ask for approval if unsure\n\n### Never:\n- Invent new button styles\n- Change color schemes\n- Add decorative elements\n- Redesign existing flows\n\n---\n\n## For Scope Questions\n\n### If feature sounds useful but not planned:\n1. Check 01_PRODUCT_GUIDELINE.md (feature list)\n2. Check 05_USER_FLOW.md (workflows)\n3. If not there, **ask first**\n4. Don't build it unless approved\n\n### Even if it's easy:\n- Don't sneak in extra features\n- Don't optimize things not yet built\n- Don't add \"nice to have\" features\n- Stay focused on current phase\n\n---\n\n## For Architecture Decisions\n\n### Database decisions:\n- Consult 07_DATABASE_PLAN.md\n- Don't change schema without migration\n- Always use foreign keys\n- Test transactions\n\n### API decisions:\n- Follow 08_API_PLAN.md\n- Consistent error handling\n- Versioning from start\n- Rate limiting required\n\n### Component decisions:\n- Check 03_DESIGN_SYSTEM.md first\n- Use shadcn/ui, not custom\n- No component should be > 200 lines\n- Test each component\n\n---\n\n## For Performance Issues\n\nIf something is slow:\n1. Measure (Lighthouse, DevTools)\n2. Identify bottleneck (image, JS, API)\n3. Fix strategically (not every optimization)\n4. Test before/after\n5. Document decision\n\n**Priority:** Images > JavaScript > CSS\n\n---\n\n## For Security Issues\n\nIf security concern:\n1. Stop, don't ship\n2. Check 10_SECURITY.md\n3. Fix immediately\n4. Test the fix\n5. Document incident\n\n**Common issues:**\n- Never log secrets\n- Always validate input\n- Sanitize for XSS\n- Use HTTPS only\n- Rate limit endpoints\n\n---\n\n## For Git & Commits\n\n### Commit Message Format\n```\nfeature: add like button to gallery\n\n- Add heart icon button to photo cards\n- POST /selections endpoint to save likes\n- Toast confirmation when liked\n```\n\n### Branch Naming\n- `feature/gallery-like-button`\n- `fix/lightbox-zoom-mobile`\n- `docs/add-api-examples`\n- `chore/update-dependencies`\n\n### PR Checklist\n- [ ] Tests pass (unit + E2E)\n- [ ] No TypeScript errors\n- [ ] Mobile-responsive\n- [ ] Dark mode tested\n- [ ] No console errors\n- [ ] Accessibility checked (axe)\n- [ ] Performance checked (Lighthouse)\n- [ ] Commit messages clear\n\n---\n\n## For Testing\n\n### Test Requirements\n- New code must have tests\n- 80%+ coverage for critical paths\n- Unit tests (Vitest)\n- Integration tests (API + DB)\n- E2E tests (Playwright) for user flows\n\n### Test Mindset\n- Test behavior, not implementation\n- Mock external APIs (Google Drive, Stripe)\n- Use real database in tests (or in-memory SQLite)\n- Tests should be fast (< 1s per test)\n\n---\n\n## For Debugging\n\nIf stuck:\n1. Read the error message (often tells you the fix)\n2. Check TypeScript types (red squiggles)\n3. Check database schema (tables, columns)\n4. Check API response (DevTools Network tab)\n5. Add console.log or debugger\n6. Ask if really stuck (provide context)\n\n---\n\n## For Documentation\n\n### What to document\n- Complex algorithms (comments in code)\n- Non-obvious decisions (git commit message)\n- API changes (update 08_API_PLAN.md)\n- Database schema changes (update 07_DATABASE_PLAN.md)\n- New components (Storybook + comment)\n\n### What NOT to document\n- Obvious code (`const name = user.name` — clear)\n- Trivial functions (`getYear()` — self-explanatory)\n- Outdated comments (remove them)\n- Personal thoughts (not relevant)\n\n---\n\n## For Emergencies\n\n### If production is broken:\n1. Assess damage (how many users affected?)\n2. Implement quickfix (patch, not perfect)\n3. Deploy hotfix immediately\n4. Communicate status\n5. Root cause analysis (after fix)\n6. Improve to prevent next time\n\n### If data is corrupted:\n1. Stop writing (prevent further damage)\n2. Restore from backup\n3. Identify root cause\n4. Fix code\n5. Test thoroughly\n6. Document lesson learned\n\n---\n\n## For Phase Transitions\n\nWhen moving to next phase:\n- [ ] Current phase checklist complete\n- [ ] All tests passing\n- [ ] Code reviewed\n- [ ] Documentation
